# HTTP , HTTPS
## http
1. 평문 통신 -> 도청 가능
    - 패킷을 수집해 도청할 수 있음
    - 해결 
        - 1. 통신 자체 암호화 (SSL, TLS) + http -> https
        - 2. 콘텐츠를 암호화 -> 메세지에 포함되는 콘텐츠만 암호화

2. 상대 확인 x -> 위장이 가능
    - 상대를 확인하지 않음
    - 웹서버에 제한이 없는 경우 응답해야 함
    - 문제
        - 허가된 상대인지 모름
        - Dos 공격 방지 불가
        - 누가 요청했는지 모름
        - 요청한/ 응답 받은 클라이언트가 원래 의도한 대상인지 모름
        => SSL로 상대 확인. 상대 확인 수단으로 인증서 제공 
        신뢰가능한 제 3자 기관에서발생 -> 서버, 클라이언트가 실제하는 것을 보장
        클라이언트에서는 웹 사이트 인증에도 이용 가능 how?

3. 변조가 가능
    - 받은 내용이 보낸 것과 동일하다는 것을 확신할 수 없음
    - 중간자 공격(man in the middle)
        - 해시 값 (md5, sha-1) 확인
        디지털 서명을 확인하는 방법 => 100%는 아님, HTTPS를 사용해야 함
    
## HTTPS
통신하는 소켓 부분을 SSL, TLS로 대체하는 것
HTTP ------------------> TCP
HTTP ---> SSL(TLS) ----> TCP


HTTPS의 SSL 방식 -> 공통키 암호화, 공개키 암호화
공통키를 공개키 암호화로 교환
그 다음부터는 공통키 암호를 사용

평문에 비해 암호화는 추가적인 리소스를 사용하여 서버 한 대당 처리 가능한 요청 수가 감소
그치만 하드웨어 발달로 속도저하 정도가 감소, http 2.0을 사용하면 오히려 빠른 경우도.


# 버전별 http


## HTTP 1.0
매 요청마다 새로운 연결 - handshake, teardown 반복
연결당 하나의 요청과 응답

## HTTP 1.1
커넥션 유지. 한 개의 tcp 세션을 통해 여러 개의 콘텐츠 요청 가능
pipelining 은 응답에 상관없이 요청 보내고 서버는 요청 순으로 응답 -> HOL blocking 발생
(ㅍ의 요청이 지연되면 그 뒤 응답에 대해 blocking)
헤더. 한 개의 IP에 여러 도메인 적용
proxy-authenticate, proxy-authoriation 추가
-> 프록시가 사용자의 인증을 요구하는 것이 가능해짐
요청/응답 많아지면서 반복되는 헤더 내용이 많아짐
-> 불필요한 데이터 주고 받아 네트워크 자원 낭비

persistent connection -> 지속 시간을두어 1.0 에서의 연결 해제 과정을 하지 않아도 됨. 대신 요청 후 응답을 기다려야 함. 

## HTTP 2.0
1. http 메세지 전송방식 변화
1.0 text 형식 전달에서 요청, 응답 메세지는 프레임 단위로 나뉘고 바이너리 형식으로 인코딩.
파싱 전송 속도 향상
2. HOL blocking 개선
멀티 플렉싱 - 한 커넥션으로 동시에 여러 개의 메세지를 주고 받고, 응답은 순서에 상관없이 stream(양방향 데이터 흐름, 헤더에 고유 식별자, 우선순위 있음)으로 주고 받음
- 응답 우선 순위가 높은 것을 먼저 응답
3. 헤더 중복
클라이언트와 서버가 각각 header table 관리
이전과 동일한 필드는 table 의 index 만. 변경된 필드는 huffman encoding 후 전송.
-> 헤더 크기 경량화. 로그 시간 감소
그러나 TCP 기반으로 인한 HOL blocking 을 피할 수 없음

## HTTP 3.0
전송 계층에 UDP 기반 QUIC 로 사용
핸드쉐이크, 슬로우 스타트 필요 x
독립된 스트림으로 향상된 멀티플렉싱

첫 연결 설정을 캐싱하여 다음 연결시 사용
